## BUG-01 — Відновити редагування фестивалю зі сторони адміністратора

| Поле | Значення |
|---|---|
| **Тип** | Bug |
| **Пріоритет** | Високий |
| **Роль** | Адмін |
| **Компонент** | Frontend (сторінка конкурсу) + Backend (права доступу) |
| **Залежності** | — |

### Опис

Адміністратор не має кнопки редагування фестивалю, тому не може переглянути й змінити всі дані конкурсу (загальне, контакти, оплата, категорії, майданчики, розподіл). На скріншотах сторінки конкурсу під адміном у шапці є тільки «Подати заявку».

### Кроки відтворення

1. Увійти під роллю «Адмін».
2. Меню «Конкурси» → відкрити будь-який конкурс (наприклад, «Шехеризада»).
3. Переглянути шапку та вкладку «Деталі».

### Фактичний результат

Кнопки «Редагувати» немає, повна форма конкурсу для адміна недоступна.

### Очікуваний результат

Адмін бачить кнопку «Редагувати» для будь-якого конкурсу і відкриває повну форму (всі 6 кроків майстра) з можливістю зберегти зміни.

### Технічні нотатки

- Перевірити умову рендеру кнопки: ймовірно, вона показується лише власнику-організатору (`ownerId === currentUser.id`) і не враховує роль `ADMIN`.
- Винести перевірку в одну функцію, наприклад `canEditCompetition(user, competition) = user.role === ADMIN || competition.ownerId === user.id`, і використовувати її і на фронті, і на бекенді.
- Backend: ендпоінти оновлення конкурсу (`PUT/PATCH /competitions/:id` та вкладених сутностей) мають пропускати роль `ADMIN`.

### Критерії приймання

- [ ] Кнопка «Редагувати» є в адміна для кожного конкурсу, незалежно від власника.
- [ ] Адмін відкриває повну форму та зберігає зміни без помилок 403.
- [ ] Після збереження оновлені дані відображаються на сторінці конкурсу та в публічній частині.
- [ ] Для організатора, який не є власником конкурсу, кнопка не з'являється (регресія прав доступу).

## BUG-02 — Виправити збереження шаблонів і конкурсів з великою кількістю номінацій

| Поле | Значення |
|---|---|
| **Тип** | Bug |
| **Пріоритет** | Критичний |
| **Роль** | Адмін / Організатор |
| **Компонент** | Backend (ліміт тіла запиту, збереження) + веб-сервер |
| **Залежності** | Пов'язано з [BUG-05](#bug-05--виправити-генерацію-великої-кількості-номінацій-без-втрати-попередніх) |

### Опис

Шаблон із приблизно 1000+ номінацій не зберігається, конкурс із великою кількістю номінацій також не створюється. Під час збереження з'являється повідомлення «Не вдалося зберегти шаблон: request entity too large».

### Кроки відтворення

1. Конкурси → «Новий конкурс» → крок 4 «Категорії».
2. Обрати «Скласти власний», вказати назву шаблону.
3. Задати осі (склад, вік, ліга, стиль) так, щоб вийшло 1000+ номінацій.
4. Зберегти шаблон / завершити створення конкурсу.

### Фактичний результат

Помилка «request entity too large» (HTTP 413), шаблон і конкурс не зберігаються.

### Очікуваний результат

Шаблон і конкурс із 1000–5000 номінацій зберігаються успішно.

> 📷 *Скріншот: помилка «request entity too large» під час збереження шаблону «Східні»*

### Технічні нотатки

- Текст «request entity too large» — стандартне повідомлення HTTP 413: тіло запиту перевищує ліміт. Такий текст повертає body-parser в Express (типовий ліміт JSON — 100 KB), аналогічну помилку дає nginx (`client_max_body_size`, за замовчуванням 1 MB).
- Швидке виправлення: підняти ліміт, наприклад `express.json({ limit: '10mb' })`, і `client_max_body_size` у nginx до такого ж значення.
- Правильне виправлення: не надсилати всі номінації одним великим JSON. Варіанти:
  - (а) зберігати лише осі шаблону, а номінації генерувати на бекенді;
  - (б) зберігати пакетами по 200–500 номінацій в одній транзакції.
- У БД використовувати bulk insert (`createMany` / `insertMany`) замість вставки кожної номінації окремим запитом.
- Помилки показувати людською мовою, без технічного тексту на кшталт «request entity too large».

### Критерії приймання

- [ ] Шаблон із 1000, 2000 і 5000 номінацій зберігається без помилок.
- [ ] Конкурс із таким шаблоном успішно створюється.
- [ ] Збереження 2000 номінацій займає не більше кількох секунд (цільове значення погодити).
- [ ] У разі помилки користувач бачить зрозуміле повідомлення, введені дані у формі не губляться.

## BUG-03 — Зберігати заданий віковий діапазон категорії

| Поле | Значення |
|---|---|
| **Тип** | Bug |
| **Пріоритет** | Середній |
| **Роль** | Адмін / Організатор |
| **Компонент** | Frontend (форма осі «Вік») + Backend |
| **Залежності** | Пов'язано з [BUG-09](#bug-09--виправити-помилкову-валідацію-вікових-діапазонів-при-створенні-конкурсу) |

### Опис

Під час створення вікової категорії можна вказати власний діапазон «від–до», але після створення він змінюється на стандартний.

### Кроки відтворення

1. Крок «Категорії» → блок «Вік».
2. Ввести назву (наприклад, «Молодь 2»), вказати «від» = 22, «до» = 28, натиснути «Додати значення».
3. Зберегти шаблон / конкурс і відкрити знову.

### Фактичний результат

Діапазон підміняється стандартним значенням для цієї назви.

### Очікуваний результат

Зберігаються саме ті «від» і «до», які ввів користувач.

### Технічні нотатки

- Перевірити payload запиту: чи передаються `minAge`/`maxAge`, чи тільки назва.
- Перевірити, чи бекенд або фронт не зіставляє назву з довідником стандартних вікових груп і не перезаписує діапазон значенням з довідника.
- Додати валідацію: «від» ≤ «до», обидва поля обов'язкові, цілі числа ≥ 0.

### Критерії приймання

- [ ] Після збереження і повторного відкриття діапазон збігається з введеним.
- [ ] Діапазон однаковий у шаблоні, конкурсі, формі заявки та програмі.
- [ ] Некоректні значення («від» > «до», порожні) не дають зберегти і показують підказку.

## TASK-04 — Додати масове встановлення ознаки «Імпровізація»

| Поле | Значення |
|---|---|
| **Тип** | Task |
| **Пріоритет** | Високий |
| **Роль** | Адмін / Організатор |
| **Компонент** | Frontend (вкладка «Номінації») + Backend (bulk-оновлення) |
| **Залежності** | Потрібно для [TASK-07](#task-07--автоматично-підставляти-тривалість-виходу-залежно-від-ліги) |

### Опис

Номінацій-імпровізацій може бути близько 700. Ставити галочку «Імпровізація» в кожній окремо — дуже довго.

### Поточний стан

Ознака встановлюється лише по одній номінації.

### Очікуваний результат

Ознаку можна встановити або зняти для багатьох номінацій однією дією.

> 📷 *Скріншот: вкладка «Номінації» — 96 номінацій, імпровізації з тією самою тривалістю 2:30*

### Технічні нотатки

- У списку номінацій додати чекбокси, фільтри (стиль, ліга, вік, пошук за назвою) і дію «Вибрати всі відфільтровані».
- Масові дії: «Позначити як імпровізацію» / «Зняти ознаку».
- Додатково (рекомендовано): ознака на рівні стилю в шаблоні — якщо стиль «Імпровізація …» позначений як імпровізація, усі його номінації успадковують ознаку автоматично.
- Backend: `PATCH /competitions/:id/nominations/bulk` з тілом `{ ids | filter, isImprovisation }`. Для 700+ номінацій краще передавати фільтр, а не список id (див. [BUG-02](#bug-02--виправити-збереження-шаблонів-і-конкурсів-з-великою-кількістю-номінацій)).

### Критерії приймання

- [ ] Можна вибрати всі номінації за фільтром (наприклад, стиль містить «Імпровізація») і позначити їх однією дією.
- [ ] Операція для 700+ номінацій виконується без помилок і таймаутів.
- [ ] Після оновлення сторінки ознака збережена.
- [ ] Можна масово зняти ознаку.

## BUG-05 — Виправити генерацію великої кількості номінацій без втрати попередніх

| Поле | Значення |
|---|---|
| **Тип** | Bug |
| **Пріоритет** | Критичний |
| **Роль** | Адмін / Організатор |
| **Компонент** | Frontend (генерація) + Backend |
| **Залежності** | Пов'язано з [BUG-02](#bug-02--виправити-збереження-шаблонів-і-конкурсів-з-великою-кількістю-номінацій) |

### Опис

За один раз генерується до 2000 номінацій. Якщо згенерувати ще, попередньо згенеровані зникають, тому повний набір номінацій сформувати неможливо.

### Кроки відтворення

1. Крок «Категорії» → задати осі на понад 2000 номінацій.
2. Згенерувати номінації.
3. Змінити осі та згенерувати ще раз.

### Фактичний результат

Другий запуск генерації замінює перший набір, частина номінацій губиться.

### Очікуваний результат

Повторна генерація додає нові номінації до вже існуючих без видалення.

### Технічні нотатки

- Ймовірна причина: результат генерації записується замість поточного списку (`setNominations(generated)`) або бекенд видаляє всі номінації конкурсу перед вставкою.
- Потрібен режим злиття: нові номінації додаються, дублікати відкидаються за ключем *склад + вік + ліга + стиль*.
- Прибрати штучний ліміт 2000 або генерувати частинами без втрати результату.
- Показувати підсумок: «додано X, пропущено дублікатів Y, усього Z».

### Критерії приймання

- [ ] Повторна генерація не видаляє існуючі номінації.
- [ ] Дублікати не створюються.
- [ ] Можна сформувати набір понад 2000 номінацій і зберегти його (разом з BUG-02).
- [ ] Користувач бачить підсумок генерації.

## BUG-06 — Виправити обрізання тексту у формі спеціальної категорії

| Поле | Значення |
|---|---|
| **Тип** | Bug |
| **Пріоритет** | Низький |
| **Роль** | Адмін / Організатор |
| **Компонент** | Frontend (модальне вікно «Спеціальна категорія») |
| **Залежності** | — |

### Опис

У модальному вікні «Спеціальна категорія» частина тексту не видно повністю.

### Кроки відтворення

1. Вкладка «Номінації» → «+ Додати спеціальну категорію».
2. У блоці «Вік» почати вводити назву вікової групи.

### Фактичний результат

Поле назви дуже вузьке («Нове…»); у випадному списку значення обрізані до «Моло», «Моло», «Моло», тож неможливо відрізнити «Молодь 1» від «Молодь 2»; верхній блок вікна заходить під заголовок, і його підпис обрізаний.

### Очікуваний результат

Усі назви, підписи й значення видно повністю.

> 📷 *Скріншот: модалка «Спеціальна категорія» — поле віку та випадний список обрізані*

### Технічні нотатки

- Задати полю назви `min-width` (або `flex: 1`), а полям «від»/«до» — фіксовану ширину.
- Ширина випадного списку — не менша за найдовше значення (`min-width: max-content`) або з переносом тексту.
- Зробити шапку модалки фіксованою, а прокрутку — лише для тіла (`overflow-y: auto`), щоб контент не заходив під заголовок.

### Критерії приймання

- [ ] Назви вікових груп видно повністю в полі та у випадному списку.
- [ ] Верхній блок модалки не обрізається.
- [ ] Перевірено на ширинах 375, 768, 1280 і 1920 px.

## TASK-07 — Автоматично підставляти тривалість виходу залежно від ліги

| Поле | Значення |
|---|---|
| **Тип** | Task |
| **Пріоритет** | Середній |
| **Роль** | Адмін / Організатор |
| **Компонент** | Backend (логіка тривалості) + Frontend |
| **Залежності** | Залежить від [TASK-04](#task-04--додати-масове-встановлення-ознаки-імпровізація); пов'язано з [BUG-10](#bug-10--синхронізувати-тривалість-ліг-після-зміни-тривалості-в-таймінгу) |

### Опис

Тривалість усіх виходів, крім імпровізацій, має підтягуватися з налаштувань ліги. Зараз усі номінації мають однакові 2:30 незалежно від ліги (при цьому у «Таймінгах» задано Вища — 120 с, Відкрита — 90 с, Початківці — 75 с).

### Поточний стан

Тривалість номінації не залежить від ліги.

### Очікуваний результат

Тривалість звичайної номінації = тривалість її ліги; для імпровізацій — окрема тривалість.

### Технічні нотатки

- Правило:
  ```ts
  duration = nomination.isImprovisation
    ? improvisationDuration
    : leagueDuration[nomination.leagueId];
  ```
- Дозволити ручне перевизначення тривалості окремої номінації з прапорцем `durationOverridden`, щоб автоматика його не затирала.
- Застосовувати правило при створенні номінацій і при зміні тривалості ліги (див. BUG-10).

### Критерії приймання

- [ ] Нова номінація Відкритої ліги отримує 1:30, Вищої — 2:00, Початківців — 1:15 (згідно з налаштуваннями).
- [ ] Імпровізації мають окрему тривалість, логіка ліг її не перезаписує.
- [ ] Ручно змінена тривалість номінації зберігається.

## BUG-09 — Виправити помилкову валідацію вікових діапазонів при створенні конкурсу

| Поле | Значення |
|---|---|
| **Тип** | Bug |
| **Пріоритет** | Критичний |
| **Роль** | Адмін / Організатор |
| **Компонент** | Frontend + Backend (валідація шаблону) |
| **Залежності** | Пов'язано з [BUG-03](#bug-03--зберігати-заданий-віковий-діапазон-категорії) |

### Опис

Конкурс неможливо створити через перетин вікових діапазонів, хоча ці діапазони не використовуються в номінаціях.

### Кроки відтворення

1. Новий конкурс → «Категорії» → «Скласти власний».
2. У блоці «Вік» залишити лише «Молодь 1 (16–21)», «Молодь 2 (22–28)», «Юніори 1 (12–13)», «Юніори 2 (14–15)».
3. Зберегти шаблон.

### Фактичний результат

Помилка «Вікові діапазони шаблону перетинаються…» зі згадкою «Дорослі (16–100)» і «Підлітки (12–15)», яких серед вибраних значень немає.

### Очікуваний результат

Валідуються лише ті діапазони, які реально використовуються в номінаціях; конкурс створюється.

> 📷 *Скріншот: помилка про перетин діапазонів «Дорослі» та «Підлітки», яких немає серед вибраних*

### Технічні нотатки

- Ймовірна причина: валідація бере не поточні вибрані значення, а всі діапазони (довідник стандартних груп або видалені значення, що лишилися в стані форми).
- Валідацію виконувати тільки на наборі вікових груп, які використовуються в номінаціях конкурсу.
- Під час видалення значення (×) прибирати його зі стану форми та з payload.
- Погодити з замовником: чи перетин діапазонів має блокувати збереження, чи достатньо попередження.

### Критерії приймання

- [ ] Сценарій зі скріншоту зберігається без помилок.
- [ ] Невикористані або видалені діапазони не впливають на валідацію.
- [ ] Якщо перетинаються реально використані діапазони, повідомлення називає саме їх.

## BUG-10 — Синхронізувати тривалість ліг після зміни тривалості в таймінгу

| Поле | Значення |
|---|---|
| **Тип** | Bug |
| **Пріоритет** | Середній |
| **Роль** | Адмін / Організатор |
| **Компонент** | Backend + Frontend (вкладки «Таймінги», «Номінації», «Програма») |
| **Залежності** | Пов'язано з [TASK-07](#task-07--автоматично-підставляти-тривалість-виходу-залежно-від-ліги) |

### Опис

Після встановлення нової тривалості по лігах у вкладці «Таймінги» тривалість номінацій не змінюється.

### Кроки відтворення

1. Вкладка «Таймінги» → змінити тривалість, наприклад, Відкритої ліги на 90 с, зберегти.
2. Перейти у «Номінації» і «Програма».

### Фактичний результат

Номінації зберігають стару тривалість (2:30).

### Очікуваний результат

Тривалість номінацій відповідної ліги оновлюється (крім імпровізацій і вручну змінених).

### Технічні нотатки

- Під час збереження тривалості ліги оновлювати `duration` номінацій цієї ліги, де `isImprovisation = false` і `durationOverridden = false`, або обчислювати тривалість під час читання.
- Після збереження оновлювати дані на фронті (інвалідація кешу / повторний запит).
- У «Таймінгах» є підказка, що зміна не перераховує вже сформовані відділення. Варто запропонувати перерахунок одразу після збереження (кнопка або діалог).

### Критерії приймання

- [ ] Після зміни тривалості ліги номінації цієї ліги показують нову тривалість.
- [ ] Після оновлення сторінки значення актуальні.
- [ ] Імпровізації та вручну змінені номінації не перезаписуються.
- [ ] Після перерахунку розклад програми враховує нову тривалість.
